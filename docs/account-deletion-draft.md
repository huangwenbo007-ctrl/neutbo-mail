# Account deletion: incomplete development draft

Do not deploy this branch. Deletion routes are enabled only in an isolated preview; the production cleanup scheduler is not connected.

## Agreed product behavior

- Disable a user's account when deletion is requested; keep it recoverable for 30 days.
- During the grace period, the owner requests recovery through support@neutbo.com; an administrator must verify identity before restoring it.
- After the grace period, begin deleting account data and attachments. Backups, provider logs, and shared objects need separately documented retention and deletion behavior.

## Implemented in this draft

- D1 state transitions mark a user deleted, record the deadline, increment the session generation, allow an atomic pre-deadline restoration, and claim an expired request for purge.
- The deletion primitive requires the configured administrator email and refuses to mark that account deleted. Callers must obtain this value from trusted server configuration, not the request; other privileged roles still require review.
- Login and protected API requests read the account status and generation from D1. Old tokens become invalid even after a restoration; tokens issued before this migration are treated as generation zero.
- Administrator restoration is guarded against expiry and concurrent purge; new incoming mail is rejected for deleted accounts.
- The prototype coordinates deletion transitions with inbound and on-site recipient writes using a per-account reservation, and rechecks the recipient before saving. Isolated Workers tests cover normal delivery, deleted recipients and lock contention. This does not cover every writer or older deployed workers, and lock contention currently raises an error whose SMTP retry behavior has not been verified.
- The legacy administrator user-deletion path acquires the same account reservation and refuses accounts with deletion requests, preserving their recovery period. Other legacy deletion paths remain to be audited.
- The legacy self-delete path is temporarily disabled in this draft, because its existing settings can trigger immediate permanent deletion. Replace it with a reauthenticated grace-period request only when the complete flow is ready.
- A disconnected password-check prototype reserves at most five attempts per account per 15 minutes in D1, including successful attempts. It is not a standalone authorization proof and is not connected to any endpoint. Test-only clock injection must never be exposed to clients.
- Self-service password change requires the existing password and atomically increments session generation, forcing a new login. This path and the UI have local integration/build coverage; a Google-only account without a password still needs a separately verified recovery flow.
- The administrator password-reset path also increments session generation atomically with the password change. A Workers test confirms an existing session and old password stop working.
- A password-deletion prototype checks the current password and makes the deletion request only if the same password hash and salt still match at the atomic database update. An isolated-only API route requires an explicit confirmation and a flag enabled only in the test runner. Workers tests cover authentication, wrong password, administrator protection and a password change during verification. The existing security and release blockers still apply; never enable the test flag in production.
- The prototype compares fixed-length password digest buffers with Workers `timingSafeEqual`; this does not change the existing password hashing algorithm or secure other password checks.
- A test-only Google identity flow uses a server-created one-time, session-bound challenge, PKCE and nonce, verifies Google's RS256 signature and claims, checks a recent `auth_time` and the currently bound Google subject, then atomically disables the account. Simulated-provider tests include incorrect identity, reused or expired challenges and wrong sessions. A real Google test returned to the preview but failed closed; no deletion occurred. The exact failing claim was not recorded and has not been identified.
- The requested replacement is a test-only email-code flow. It sends to the linked Google contact taken solely from a Google userinfo response with `email_verified=true`, never from client input or legacy oauth.username. Existing linked users must log in with that Google account once after this preview feature is installed to establish the verified contact; this is enrollment, not a Google sign-in at deletion time. Codes are session-bound, expire after five minutes, have bounded attempts and sends, and are consumed with the deletion transaction. Real Gmail testing on the isolated preview confirmed that the code was delivered and accepted, the disposable account was disabled, the code was consumed and the pending request has a 30-day interval. Independent security review and broader lifecycle testing are still needed.
- A draft settings dialog explains the recovery period and offers a password or linked Google verification. It is disabled unless the frontend is explicitly built with the test-only flag; default and test-flag builds succeed. The password route was exercised in a browser, but Google verification did not pass and accessibility checks remain outstanding.
- A draft purge staging operation queues attachment keys as `UNRESOLVED` and deletes only the selected user's metadata in one transaction. It never guesses the original storage provider or deletes the underlying objects.
- Staging refuses to remove metadata when the user has been reactivated, even if a stale request says it is being purged. Isolated SQLite and Workers/D1 tests cover this, a harmless retry after staging, and preservation of another user's account.
- Staging clears the deleted creator's references in shared roles and invitation codes while retaining those records. Isolated tests cover preservation and other users' references; operational and privacy review is still required.
- Draft per-object reservations and queue processing have isolated SQLite tests for shared references, failed deletion, retry and lock contention. Incoming, outgoing, inline and on-site-copy draft paths use the reservation. Targeted Workers tests cover incoming/outgoing contention and stale on-site references; the scheduler remains disconnected and this does not yet protect actual attachments.
- The draft object cleaner now refuses to delete an unreferenced file unless a trusted, lock-protected origin record names the same storage type and exact store identity as the selected deletion target. A missing or conflicting origin remains unresolved; shared files stay queued for a later retry. Recording origins is an isolated primitive only: real writer paths do not yet call it, target identities and configuration-change handling are not established, and cleanup remains disconnected.
- Workers binding tests also exercise shared-file preservation and failure/retry with D1 and KV. An independent Cloudflare preview database, KV namespace, and preview-only JWT secret were configured; a disposable test account successfully logged in, rejected a wrong password, requested deletion, and had its old session rejected. D1 recorded the pending request with a 30-day interval. The preview still requires complete recovery, Google identity and cleanup tests; it is not production-ready.
- The legacy attachment-reference removal path now queues object keys as `UNRESOLVED` in the same D1 transaction and does not physically delete them. This conservatively protects shared files but retains storage until a verified origin and safe cleanup mechanism exist; it is not complete erasure.
- Applied the draft schema twice to the disposable Cloudflare preview database and checked that existing user, account and pending-request counts remained unchanged. Production schema was inspected read-only; none of the six new lifecycle tables existed at that time. No production migration has been run.

## Release blockers

- Complete independent security review and end-to-end tests for password and Google-email-code confirmation, including provider failures, linked-contact changes, concurrency, and session revocation. The old Google reauthentication route is an isolated experimental route and must not be enabled in production.
- The Google test project is in Testing status; its session-age claim setting is disabled and unavailable. Google documents that the security bundle requires a published, verified application and explicitly says Google Account reauthentication requests are not supported. Even an enabled `auth_time` reports the last Google sign-in and may be old; selecting an existing Google account is not proof of fresh authentication. Design an independent step-up mechanism and test it end to end; do not weaken the current check. See https://developers.google.com/identity/siwg/security-bundle.
- Registration verifies an external email but does not persist a verified recovery address linked to the account; it cannot currently be used for recovery. The Google contact applies only to linked Google users and is not a general recovery address. Define a safe enrollment and change process before relying on either for support recovery.
- The password-check prototype needs an independently reviewable design for brute-force and account-lockout abuse, proof binding, expiry, single use, password-change races, and token revocation before use. Google reauthentication needs separate validation. Existing legacy password hashing requires a separate upgrade plan.
- Complete password recovery for Google-only accounts, validate rate-limit lockout behavior, review the administrator reset authorization flow and plan the legacy hash upgrade.
- Complete scheduler integration, durable retry, operational monitoring and idempotent cleanup for requests stuck in `purging`.
- Existing attachment keys are content hashes, shared by different users and reused by multiple writer paths. A reference-count check alone races with new writes. Coordinate **all** attachment writers and cleanup before deleting an object; test concurrent writes, shared keys and retries.
- The draft rejects incoming mail if attachment storage fails, marks the message hidden/failed, and records attempted object keys. Targeted Workers tests cover rejection and the normal receive path. This is a permanent SMTP rejection, not an automatic retry guarantee. If D1 itself is unavailable, failure details may not be recorded; build monitoring and a recovery procedure before release.
- Audit every attachment-reference removal path and coordinate account writes with eventual cleanup. The changed legacy path keeps physical objects and records an unresolved queue item instead of deleting them. Per-account deletion still needs protection against every concurrent new attachment.
- The draft reservation intentionally has no automatic expiry: clearing a lock while a previous writer or cleaner is still running can corrupt data. Define monitored, verified recovery for stranded locks, or replace it with a fully fenced coordination design before deployment.
- A reservation release can fail after a write has committed. Define idempotent operation identifiers and retry behavior so an error does not lead to duplicate delivered emails.
- Existing attachments do not store their original storage provider. A settings change can make the current provider different from where an old object lives. Determine and record the correct provider and preserve credentials until cleanup completes; do not blindly use the current setting.
- A read-only production check on 2026-11-16 found zero attachment rows, zero `attachments/` keys in the currently bound production KV namespace, no S3 bucket/endpoint configuration, and no R2 binding. This is a point-in-time observation, not proof about historical stores, backups, other namespaces, or future writes. Recheck during any migration and do not infer historical origin from current settings.
- Prevent every concurrent/in-flight writer from re-creating data after purge begins. Inbound and on-site delivery are only partly coordinated; audit all other account and attachment writes, older deployed versions, lock ordering, release failures, and SMTP behavior under contention before release.
- Define how to stop, retry and observe KV/R2/S3 deletion, including partial failures and provider changes. Ensure a shared file is never removed while referenced by any other user.
- Audit all other copies, including object storage, cached or forwarded messages, database backups and provider logs. Do not promise complete erasure or a fixed retention period until verified.
- Review remaining user identifiers in session-generation/deletion tables and all other records. Verify shared role and invitation-code behavior and anonymization against existing deployment data; don't promise complete removal without a safe retention design.
- Review compatibility with legacy admin deletion/restore operations, account aliases, disabled registration, existing sessions, and missing/deleted database rows.
- Provide an explicit production migration and rollback plan. Without `account_session_generation`, the draft auth changes fail closed; adding code before the table would disrupt login.
- Run Workers integration tests and realistic storage failure/concurrency tests; perform end-to-end tests only on isolated, disposable resources. Do not touch production before all checks and migration/rollback are ready.
